Start here

DueSoon is a shared deadline board for one class: anyone adds an assignment, quiz or exam, everyone sees it sorted by due date, each student ticks off their own work and sees how many classmates finished. This page explains every part of the code. Each member owns one feature from the screen to the database: their Flutter screens and the server code behind them. How it fits together

The Flutter app never touches the database. It sends HTTP requests to our Express API, which checks the login token and the rules, reads/writes the database, and answers with JSON.

Login token

After login the server gives a token. Session keeps it; ApiService sends it with every request so the server knows who you are.

Server is the rule

The app checks forms to give quick messages, but the server checks everything again (past dates, who may edit).

days_left comes from the server

"Today" is the Bangkok date on the server, so every phone shows the same "2 days left". The app only picks colors and words.

Prisma instead of mysql2

Class used Express + mysql2 + MySQL (TiDB). We use Express + Prisma + Postgres (Neon): Prisma writes the SQL for us. Routes, REST and JSON work the same way.

Refresh after changes

A screen that changed something closes with Navigator.pop(context, true); the screen below reloads its list.

Practice questions

Questions a teacher might ask about each part. Try to answer before opening.

M1 Getting in

Why does Splash use pushReplacement instead of push?

So pressing Back on Login doesn't go back to the splash screen; the splash is removed from the history.

How does the form know a field is wrong?

Each TextFormField has a validator that returns an error text or null. _formKey.currentState!.validate() runs them all and shows the red messages.

Where is the login stored? What happens when you close the app?

In Session (static fields, memory only). Closing the app forgets it, so you log in again.

Why check mounted after await?

The user might have left the screen while waiting for the server; using context then would crash.

What happens if the token expires?

The API answers 401; showApiError clears the session and sends you to Login with "Session expired".

Backend: how does the server know who is calling?

The app sends Authorization: Bearer <token>. The requireAuth middleware verifies the JWT and sets req.user; routes only trust req.user.id, never an id from the body.

Backend: how are passwords stored?

As a bcrypt hash, never the real password. Login compares the typed password with the hash.

Backend: why the same message for wrong password and unknown email?

So nobody can find out which emails have accounts.

M2 Seeing tasks

How do the three tabs work?

DefaultTabController + TabBar + TabBarView. Each page is the same TaskListTab widget with a different filter (week / all / done).

How does JSON become something the app can show?

ApiService.getTasks decodes the JSON into a List of Maps, and Task.fromJson turns each Map into a Task.

Who decides "2 days left"? The app or the server?

The server sends days_left (Bangkok date). The app only picks a color and text from it, so every phone agrees.

Why does the checkbox show a spinner instead of ticking immediately?

It waits for the server and reloads, so the screen always shows what the server really saved.

Why not use ListTile for the cards?

ListTile has a fixed height and cut off the second line when a title wrapped, so we built the row ourselves.

Backend: how does the server pick This Week tasks?

Tasks due on or before today + 7 days (so overdue ones too) that are not in task_done for me, sorted by due date.

Backend: how can done be different for each student?

The task_done table has one row per (user, task). Ticking adds my row; my classmates have their own.

Backend: you used Prisma, not mysql2. What is it?

A library that writes the SQL for us: findMany = SELECT, create = INSERT. Same REST + database idea as class, with Postgres instead of MySQL.

M3 Managing tasks

How does the detail screen know which task to show?

The list passes only the task id; the detail screen loads the full task with GET /tasks/:id.

How does the list know to refresh after you add, edit or delete?

Screens close with Navigator.pop(context, true); the screen that opened them awaits that result and reloads when it's true.

How is one form used for both Add and Edit?

existing is null for Add; for Edit it's the task, so the fields are pre-filled and Save calls PUT instead of POST.

Why can't other people edit my task?

The app hides Edit/Delete when is_owner is false, and the server also refuses with 403. The server is the real rule.

Why can't I pick a past date?

The date picker starts at today (Bangkok time) and the validator and server reject past dates for new tasks.

Backend: what is the difference between 403 and 404?

404 = the task doesn't exist. 403 = it exists but you didn't create it, so you may not change it. checkOwner checks 404 first, then 403.

Backend: which HTTP methods does your part use?

GET /tasks/:id (read), POST /tasks (create → 201), PUT /tasks/:id (update), DELETE /tasks/:id (delete → 204): the four CRUD operations.

Backend: what happens to done marks when a task is deleted?

They're deleted too: the database removes the task_done rows automatically (ON DELETE CASCADE).
